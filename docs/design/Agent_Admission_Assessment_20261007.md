# Agent 工具与依赖准入检查器市场与工程评估

评估日期：2026 年 10 月 7 日。适用比赛：汉客松 S1 与 ETH Wuhan 2026。面向团队负责人、技术负责人及评委。

这个方向值得继续，但必须收窄到一个能够证明价值的使用环节。建议首发面向以太坊研究 Agent：在调用陌生链上数据服务前检查来源、权限及可验证的软件信息，在调用后验收数据，并留下其他使用者能够核查的证据。一般依赖扫描、MCP 安全扫描、工具隔离和企业网关已经有直接竞品；“同类产品少且不成熟”不能成为主要立项依据。

当前应作出的决策是：以“针对指定任务的服务准入与交付验收”为核心，把依赖扫描作为输入插件，把区块链用于公开证据承诺和历史记录。市场需求有政府报告、学术研究及商业产品支持，付费意愿、客户规模与自身效果仍需实际验证。[1–6]

本次附件是 DAO 提案言行一致性审查方案。它提供了“声明、实际效果、确定性对账、证据”的相关设计思路；本评估针对用户本次指定的 Agent 工具与依赖准入检查器。未提供该检查器的源码和运行记录，因此以下工程状态均为建设要求，不构成已实现或已通过验收的声明。比赛规则及提交时间以用户提供的手册内容为依据。

**1 立项判断与赛道定位**

| 维度 | 判断 | 必须补齐的证据 |
| --- | --- | --- |
| 真实问题 | 外部工具可能带来权限滥用、供应链风险、提示注入和不可靠数据，问题成立 | 目标客户现有流程、实际失败案例及处置成本 |
| 市场竞争 | 扫描与网关市场已有供给，不能主张无人竞争 | 与至少一个扫描器及一个网关比较同一组任务 |
| 数据可获取性 | 公开漏洞、依赖和以太坊数据可获得；远程服务真实部署信息不一定可获得 | 实际接口联调、覆盖率、授权范围、数据更新时间 |
| 技术可行性 | 指定语言、指定工具类型及固定任务下可落地 | 网关阻断、结果核验、切换和证据回放的完整演示 |
| GCC 赛道结合 | 最契合赛题一的服务探测、交付验收、公共记录 | 实际使用结果成为下一位使用者可复核的信息 |
| BOT Chain 结合 | 可以承担公开证据登记；EVM 兼容便于迁移 | 主网合约地址、成功交易、事件和可访问浏览器链接 |
| 创新性 | 组合本身不足，价值取决于任务约束、持续失效和公共证据的有效结合 | 同样风险下比基线更少错误接纳、更低接入成本或更好的验收效果 |
| 先发优势 | 不具备广义扫描器或工具登记的先发资格 | 在明确客户群建立协议、验证器、集成和有标签的数据资产 |
| 商业确定性 | 仍是待验证假设 | 有预算的决策人、真实部署试点及续用意愿 |

GCC 赛题一关注陌生服务当前是否可用、准确和履约。只上传一个依赖漏洞报告，无法充分回答这个问题。以太坊数据应进入核心验收流程，而不是仅在最终报告上加一个上链按钮。GCC 赛题二可作为后续用户场景：异动调查 Agent 采购数据时使用本工具；本次应首先聚焦赛题一。

推荐定位：**为以太坊研究 Agent 提供按任务限制的工具准入、数据验收与公共证据。**

对应的问题是：这个服务的身份和元数据能否核对；它是否在本任务权限范围内；本次返回是否满足指定链、区块和数据条件；失败后能否阻断、切换，并留下可复核的记录。任何一次检查都应标明对象、版本、时点、范围和未覆盖项。

**2 竞争与客户选择**

| 已有产品或规范 | 官方材料明确描述的能力 | 对本项目的影响 |
| --- | --- | --- |
| Snyk Agent Scan | Agent、MCP server、skill 的安全发现与扫描；配置扫描可能启动本地服务器或发起外部连接 | 已存在直接竞争；发现提示注入或可疑工具描述本身不足以成为差异点 [4] |
| Invariant MCP-Scan 的前序研究 | 工具投毒、工具描述变化，以及通过哈希固定工具的设计 | 属于已有技术沿革，不应将此行与 Agent Scan 简单重复计算为两个独立市场玩家；“检测工具换版本”不能宣称独创 [5] |
| Docker MCP Gateway | 容器隔离、凭证注入、权限及网络限制、调用日志 | 隔离和代理调用已有实现，可复用其理念或组件 [6] |
| Azure API Management | MCP 认证、授权、监控、限流及企业目录 | 企业治理网关也已有供给；客户可能选择既有平台 [7] |
| ERC-8004 | Agent 身份、反馈和验证的通用接口 | 可用来关联公共证据；登记不证明能力真实，仍有女巫攻击风险 [8] |
| ERC-8257 | 官方页面标注为 Draft；工具登记、元数据哈希与可扩展访问条件 | “链上工具登记加权限条件”已经被探索，宜考虑兼容 [9] |
| ERC-8126 | 官方页面包含 Agent 专门验证及可选链上验证结果关联 | Agent 安全验证也不是空白方向；没有实现相应流程不得声称符合该规范 [10] |

上述比较依据各方公开文档描述，不等于独立测评，也不能据此断言这些产品没有支持其他能力。应对同一服务、同一任务、同一异常输入进行实测，再判断本项目是否有增量。

优先客户是接入第三方工具的 Agent 平台团队、面向链上研究与风险监测的 Agent 开发团队，以及需要统一管理工具接入的基础设施运营者。企业购买者通常是平台或安全负责人；最终使用者可以是开发人员或研究人员。黑客松用户与商业付费客户不必完全相同。

商业假设是：这些团队愿意为减少逐次人工核对、重复集成、错误数据传播和失控工具调用支付费用。开源部分可包括验收规则、验证器、证据格式及演示数据；收费部分可围绕私有部署、团队策略、持续监测、支持及企业审计展开。开放的公共物品与收费的运营服务可以并存。

提出以下客户验证停点，数量是建议目标，不是已获得结果：访谈约 10 位符合目标画像的负责人，至少取得 3 个可复现的问题，并找到 2 个愿意接入真实流程的试点。如果对方只需要免费的一次性扫描，且没有持续任务验收需求，应缩小产品或更换切口。

测量人工核对时间、准入维护时间、服务故障影响、网关新增时延、误拒绝率及试点续用率。避免以安全事故的最大损失直接推算市场规模。建立自下而上的模型：符合条件的团队数量、可接入比例、实际合同金额和维护成本；这几个输入均需验证。

**3 数据架构与权威性**

| 数据层 | 首选来源与获取方式 | 能够支持的结论 | 主要边界 |
| --- | --- | --- | --- |
| 开源依赖漏洞 | OSV 按 ecosystem、package、version 或 commit 查询；支持批量及数据导出 | 指定组件版本命中已披露的受影响范围 | 无命中不等于不存在漏洞；应保留来源与记录版本 [11–12] |
| 漏洞与恶意软件通报 | GitHub Global Advisories REST API | 维护者或数据库收录的公告及受影响版本 | 默认列表排除 malware；需要单独查询相关类型 [13] |
| 已被利用漏洞 | CISA KEV 及其官方 GitHub 镜像 | CISA 确认在野利用的漏洞信号 | 覆盖的是已确认集合；不在目录不能解释为安全 [14] |
| 公共依赖图 | deps.dev v3 API | 指定包版本的公共依赖、许可信息、已知公告 | 实际安装图以本次锁文件或构建产物为准；公共图不能代替实际环境 [15] |
| 构建与签名 | 发布者提供的 Sigstore 验证材料及 SLSA provenance | 产物摘要、签名身份、签发方及构建来源可按预期核对 | 合法签名或来源不证明代码无恶意；缺失材料应标为未验证 [16–17] |
| 以太坊状态 | 自有节点，或不同运营者的 RPC 对照；固定区块查询 | 在相同链和区块下核对余额、代码、交易回执等 | 两个 URL 可能共享同一上游；一致回答不构成独立密码学证明 [18–19] |
| 工具接口 | MCP 接口、发布清单、代码产物与受控探测 | 接口存在、声明能力、观测到的行为及可验证产物 | 工具描述与注解来自服务方，不能直接当成权限事实 [20] |
| 公共验收记录 | 自己的可复核测试、真实使用结果、第三方验证 | 特定调用条件下通过或失败的观测 | 权威数据库不会自动提供所有 Agent 服务的实时真伪标签 |

OSV 的批量查询主要返回漏洞标识和修改时间，需按标识继续获取完整记录，并处理分页。OSV 会聚合包括 GitHub Advisory Database 在内的来源，因此同一 GHSA 在两个接口出现不算两份独立证据。CVE、GHSA、OSV 的别名应归并后保留原始关系。[11–12]

需要分别保存来源发布时间、来源修改时间、系统获取时间、任务执行时间、数据所指区块、有效期和原始内容摘要。第三方自己的 `updatedAt` 只能作为声明，不能直接作为新鲜度的证明。记录原始响应和规范化结果，才能重放当时的判断。

针对链上任务，先确定参考链和参考区块，再要求所有对比结果使用相同区块。Ethereum JSON-RPC 有 `safe`、`finalized` 等标签；支持 EIP-1898 的服务可使用 `blockHash` 与 `requireCanonical`。不支持时记录降级方式，并检查查询前后的区块哈希。历史研究允许明确的旧区块；需要当前数据的任务才按允许的落后窗口拒绝过期结果。[18–19]

同步策略分三类：工具及产物变更触发重新准入；漏洞公告增量同步并令受影响票据失效；每次链上调用重新核对请求对应的区块与结果。缓存键至少绑定对象摘要、任务策略、证据快照和验证器版本。缓存未过期不代表服务的当前回答无需验收。

漏洞源更新周期、允许的数据落后窗口、票据 TTL 应按任务风险设置，并用日志测量实际延迟。源停更、超时或相互矛盾时，应输出 INCONCLUSIVE 或转入受控待核验状态。系统不得把无法检查转换成通过。

权威性需要按字段确定：CISA 能支持在野利用判断，发布者及构建签名支持产物来源，节点及区块支持链上状态判断，受控调用支持履约观测。产品不能把一个“权威总分”代替这些不同的事实。

**4 检查对象与安全边界**

软件依赖准入、工具能力准入、服务交付验收必须分别建模。一个 npm 包版本的漏洞报告不能证明托管服务正在运行那个版本；一个远程工具的 SBOM 可能只是运营方声明；一个合法域名或链上地址也不能证明本次返回正确。

| 威胁 | 必需控制 | 可观察的验收证据 |
| --- | --- | --- |
| 检查配置时执行恶意命令 | 先解析配置，禁止在主环境运行任意命令；动态探测在隔离工作器进行 | 恶意 stdio 配置不能访问宿主文件、凭证或 Docker socket |
| 工具投毒与描述变化 | 不可信文本隔离；元数据摘要固定；变更触发重新检查 | 旧准入票据在工具描述或 schema 变化后失效 |
| 提示注入扩大权限 | 权限由受信策略和后端执行；LLM 无权改策略或取得密钥 | 即使模型提出越权调用，也被网关拒绝 |
| SSRF 与 DNS 重绑定 | 受限出网；拒绝未授权内网、链路本地及 IPv6 目标；逐跳校验重定向；避免检查与连接解析不同 | 直接地址、重定向、IPv6、重绑定测试被阻断 |
| OAuth 令牌混用 | 验证 audience、issuer 和授权范围；不盲目透传令牌；凭证由网关管理 | 错误目标、过期和越范围令牌不能调用工具 |
| 依赖或发布产物被替换 | 版本与摘要固定；可用时校验来源和签名 | 同名同版本但不同摘要的产物不能复用票据 |
| 数据过期、错链或错值 | 同链同区块核对；整数精度与字段校验；任务新鲜度检查 | 旧区块、错误链、余额差异进入拒绝或待核验 |
| 网关被绕过 | Agent 的外部连接及凭证只可通过网关；网关同时检查 caller 与请求参数 | 直接访问后端或伪造调用不能绕过 |
| 重放与检查后切换 | 票据绑定任务、调用者、工具版本、参数摘要、期限及 nonce；调用时重新验证 | 另一任务、另一调用者或过期票据被拒绝 |
| 恶意输入消耗资源 | 超时、大小、CPU、内存、并发与递归预算 | 超大 schema、无响应服务或无限调用被终止 |
| 证据泄漏 | 私有原始材料和公开脱敏材料分别保存；发布前完成字段白名单 | 公共记录和模型上下文不含令牌、内部路径及用户秘密 |
| 虚假信誉与审查者串谋 | 按受信验证者筛选；证据复查；相关样本去重；支持争议与更正 | 多个新地址不能通过简单平均提高可信度 |

MCP 官方安全指南明确讨论 token passthrough、SSRF、重定向和 DNS 检查时点问题；工具规范要求将不可信服务器的 annotations 视为不可信。不能仅因 `readOnlyHint: true` 就赋予权限。[20–21]

扫描器本身是新的攻击面。Snyk Agent Scan 的官方说明指出，读取配置可能启动 stdio 服务或连接远程 URL。[4] 即使只做“检查”，也需要隔离和受限网络。容器提供有用的隔离控制，高风险不可信执行仍应根据威胁模型考虑更强隔离；本次 MVP 可以只支持受控 HTTP 数据服务，把任意包执行留待后续。

结果使用四种状态：PASS 表示在明确范围内通过检查；FAIL 表示命中确定的拒绝规则；INCONCLUSIVE 表示资料缺失或判断未闭合；ERROR 表示检查流程自身故障。最终动作另用 ALLOW、REJECT、QUARANTINE 表达，避免将运行错误误报为安全失败，或将无证据误报为安全通过。

没有发现注入文本也不保证不存在注入。安全承诺应是：在已定义的风险和权限边界内阻断违规操作，并核验可验证的数据；对未覆盖的语义欺骗和远程内部行为表达限制。AgentDojo 与 InjecAgent 的同行评审研究为外部工具数据诱导错误行动提供了实证背景，其特定模型和实验条件不能当成今天所有产品的攻击成功率。[2–3]

**5 系统职责与工作链路**

建议比赛实现一个编排 Agent，配合确定性检查工作器、执行网关和结果验证器。可增加独立解释角色，但无需用多个模型投票决定安全。复用已有扫描器，避免在短时间内重写漏洞数据库和隔离平台。

| 模块 | 职责 | 权限与输出 |
| --- | --- | --- |
| 编排 Agent | 理解研究需求、识别缺失条件、从获准候选中提出服务选择、在失败后选择替代 | 只有预定义工具入口；无钱包私钥、服务密钥、任意 shell |
| 对象解析器 | 固定工具清单、包版本、产物摘要、registry 引用和协议版本 | 将描述声明与可核实事实分开 |
| 检查工作器 | 查询漏洞及来源、检查接口、运行受控探测 | 输出带来源、时间和规则标识的发现 |
| 策略引擎 | 根据任务授权及证据签发限范围票据 | 确定性代码；模型不能降低要求或扩大权限 |
| 执行网关 | 每次调用核对 caller、票据、参数、版本、期限和预算 | 唯一持有后端服务凭证的边界；仅放行批准调用 |
| 结果验证器 | 对照链上参考、任务字段、精度、时效与一致性 | 只有验收后的事实进入正常研究结果 |
| 解释角色 | 依据规则及证据生成用户报告，指出失败和未覆盖项 | 输出必须引用证据标识；不能改动判定 |
| 证据服务与登记合约 | 保存私有原始材料、生成公开材料、签名并登记内容承诺 | 独立低权限签名器；链上提交失败不改变本地验收结论 |

工作顺序为：任务授权与参考区块确定；候选对象固定；静态检查和有限探测；策略引擎签发票据或拒绝；网关核对票据后调用；返回结果验收；通过后供 Agent 使用；失败则隔离该结果并在原授权范围内切换；生成可核查证据；将适合公开的承诺登记，供下一使用者验证。

服务选择不得仅依赖语言模型判断，至少受覆盖链、支持方法、所需区块、价格或调用预算、延迟及已验收记录约束。所有候选均失败时，应停止并呈现原因，不能反复换服务直到随便一个返回成功。

每个 skill contract 至少规定输入 schema、输出 schema、身份与权限、资源预算、错误状态和证据格式。建议接口包括：

| 接口 | 核心输入 | 核心输出与约束 |
| --- | --- | --- |
| `subject.resolve` | 工具或包引用、已批准来源 | 固定对象摘要及声明信息；不执行 arbitrary command |
| `admission.inspect` | 固定对象、任务策略、证据快照 | 分项发现和未知项；不直接授予权限 |
| `admission.evaluate` | 检查证据、受信策略版本 | 允许、拒绝或隔离；范围、期限及判定原因 |
| `tool.invoke` | 票据、caller、参数及请求标识 | 受限原始响应或明确拒绝；检查重复调用预算 |
| `result.verify` | 请求、结果、参考链与区块 | 分项验收和证据；不把未知解释为成功 |
| `evidence.verify` | 报告、签名、链上登记引用 | 摘要、签名、范围、过期和撤销检查 |
| `evidence.publish` | 已完成脱敏的公开材料 | 记录标识、提交状态和回执；不自动公开私有原件 |

准入凭据建议绑定 `subjectHash`、`manifestHash`、可用的 `artifactDigest`、`taskProfileHash`、caller、工具方法、参数范围或摘要、出网范围、预算、`policyHash`、验证器版本、证据快照、签发时间、到期时间、nonce 和签名身份。涉及 ERC-8004 时，身份引用同时包含来源链、registry 地址和 agentId，不能只保存一个可能重号的整数。[8]

远程服务只有元数据哈希时，凭据只绑定公开接口声明；它不能证明远程后端代码未改变。因此每次结果验收仍然必要。新 CVE、元数据变化、策略调整和签名撤销应使相关凭据失效；受控只读任务的续签也不能自动扩展授权。

**6 区块链承担的职责**

区块链适合给跨主体的公开验收记录提供顺序、签名主体关联和内容承诺；真实性来自可重放的核验及审查者责任。把错误报告哈希写入链上，只能证明某个主体提交过这份内容，不能证明结论正确。

采用 ERC-8004 时应保留原始证据和具体标签，而不是只上传一个总分。规范本身指出注册不能保证声明的能力有效且无恶意，并指出女巫攻击仍可能存在；信任哪些审查者、如何复核、如何处理争议，需要产品设计。[8]

比赛可使用一个简洁的只追加 EvidenceRegistry，字段包括对象与来源链引用、验收范围摘要、验证者、规则版本、公开证据摘要、URI、验收状态、时间和到期时间。更正或撤销追加新记录，并明确指向旧记录。客户端验证签发者权限及最新有效状态；旧证据仍保留用于追溯。自定义登记合约需明确标注自定义，不能仅因名称相近就声称符合 ERC-8004。

规范化建议采用经过实现验证的 RFC 8785 JSON Canonicalization Scheme，报告声明哈希算法和规范化版本，避免仅用“键排序去空格”描述。大整数、金额和链上数量以字符串表示，避免 JavaScript Number 精度损失。明确拒绝重复 JSON 键及未支持表示，不能让生产者与验证者解释出不同内容。[22]

全文保存的可用性与链上摘要完整性分别处理。即使用内容寻址存储，也应有可访问副本；只有哈希而读不到内容的公共记录难以验收。私有信息不直接上链；若仅发布私有内容摘要，仍需评估低熵字段被猜测的风险。

Ethereum 研究数据与 BOT Chain 证据登记可以分别在 chainId 1 与 677 上完成，记录清楚来源，不需要引入跨链桥。BOT Chain 官方文档给出的主网为 677、RPC `https://rpc.botchain.ai`、浏览器 `https://scan.botchain.ai`；测试网为 968。主网联调还需要验证 RPC 支持、合约运行与回执，不能从 EVM 兼容推断完全相同的节点能力或最终性规则。[23]

**7 比赛 MVP 与演示**

首发建议只支持以太坊只读数据研究、两个可切换服务、一种软件依赖生态，以及明确的余额或交易回执验收。依赖检查可对本地演示服务的锁文件和已披露漏洞进行静态查询；不得为演示真的运行已知易受攻击依赖。

| 能力 | 本次范围 | 完成判据 |
| --- | --- | --- |
| 真实任务 | 用户要求核对某个以太坊金库余额或交易事实 | 可访问交互入口，实际触发 Agent 工具调用 |
| 服务准入 | 两个受控 MCP HTTP 服务；固定清单、范围与工具方法 | 元数据变更、错误权限和过期票据可实际阻断 |
| 真实数据 | 从实际 Ethereum RPC 读取并固定参考区块 | 展示链、区块号、哈希、请求与响应来源 |
| 服务验收 | 一个正确服务，一个可注入旧区块、错误值或异常文本的故障服务 | 异常不会进入正常研究结果，Agent 切换并成功核验 |
| 依赖输入 | 一种语言生态的真实公告查询和静态锁文件样例 | 命中版本及公告可核对；远程未证明的 SBOM 标明声明性质 |
| 证据完整性 | 公共证据、签名、摘要核对与可回放查询 | 改动一处公开内容后验证失败 |
| 公共复用 | 第二个客户端读取前次证据 | 核查来源、范围、规则、期限及撤销状态；本次数据重新验收 |
| BOT 主网 | 证据登记合约及至少一次实际登记 | 成功交易、对应事件、合约地址和浏览器链接 |

建议四分钟展示：约 30 秒交代研究任务及外部服务风险；约 60 秒展示两个服务及准入范围；约 60 秒展示异常结果被验收器拒绝、Agent 切换到合格服务；约 45 秒展示公共证据及主网登记；约 45 秒展示第二客户端验签、篡改失败以及明确的覆盖边界。初评每队约 6 分钟包含问答，实际演示应控制在约 3 分半，准备略短版本。

故障服务必须明确标注为团队受控样例。其正常数据应来自真实链；异常通过受控变更构造。不要把人为故障描述成真实商户或公开服务的事故。录像和离线回放可做网络故障备份，但应标注采集时间与回放模式，不把旧数据伪装成实时结果。

未纳入本次：通用未知漏洞发现、所有语言和工具协议、任意第三方代码执行、完整抗女巫经济机制、资金托管、自动支付、跨链桥、ZK 或 TEE 部署，以及未经实验支持的全域安全认证。后续增加每项能力都需要独立威胁模型与验收规则。

**9 验证方法与停止条件**

安全功能需要验证拒绝动作和系统边界，不能只测试报告生成成功。以下为建议验收组，不是已经完成的测试数量。

| 测试组 | 关键样例 | 验收要求 |
| --- | --- | --- |
| 正常流程 | 两个不同正确服务、明确历史查询及当前查询 | 范围内通过；不同请求的正常差异不能误拒绝 |
| 数据异常 | 错链、错误区块哈希、旧快照、错误整数精度、虚假余额 | 拒绝或待核验；错误数据不进入正常事实结果 |
| 权限与变更 | 超范围工具、参数替换、caller 替换、过期票据、manifest 变化 | 网关实际拒绝；日志可回放 |
| 提示注入 | 工具描述或响应要求读取秘密、发送交易、修改策略 | 权限边界保持；同时记录研究结果是否被误导 |
| 网络与隔离 | 未授权内网、重定向、IPv6、解析切换、超时 | 网络及进程边界生效；任务可终止 |
| 供应链 | 已知受影响版本、未受影响版本、别名重复、材料缺失、摘要变化 | 版本匹配正确；去重保留来源；缺失不判通过 |
| 公共证据 | 篡改、错误签名、过期、更正和撤销、全文不可访问 | 验证失败或明确降级；不可继续当有效凭据 |
| 服务切换 | 首个服务失败、两个均失败、备用服务范围不匹配 | 仅在同一授权内切换；全部失败则停止 |
| 韧性 | API 429、公告源停更、数据库重启、RPC 分歧、链上超时 | 无静默放行；状态和证据不丢失、不冒充成功 |

比较三种配置：直接调用；只做一次静态检查；本项目的准入加每次验收。对相同请求和故障集，分别测量错误接纳、误拒绝、任务完成、服务切换成功和额外时延。已有工具可作为额外基线，其不覆盖的能力应标为范围差异而非失败。

错误接纳率为错误或违规结果被当成合格结果的次数除以该类测试次数；误拒绝率为正确且符合范围的调用被拒绝的次数除以正常测试次数。注入攻击成功率应按预先定义的攻击目标衡量，不以出现可疑文字为成功。正常任务完成率必须与攻击防护一起报告，防止把“所有调用都拒绝”当优秀防御。[2–3]

报告样本数量、构造方法、测试时间和覆盖项；小样本零失败不能外推到全面安全。模型相关测试应多次执行并留出非演示样例；确定性规则需覆盖边界版本、精度、地址与状态转换。吞吐、P50/P95 延迟和成本需要由运行记录计算，不能用预设目标充当测量结果。

**10 对评审与交付的映射**

| 通用维度 | 权重 | 应展示的事实 |
| --- | --- | --- |
| 技术完成度 | 20% | 用户输入到真实调用、拒绝、切换、验收和证据核查的闭环；干净环境启动 |
| 创新性 | 20% | 任务范围绑定、变更或过期后失效、验收证据复用的实际增量；明确与现有能力比较 |
| 场景价值 | 20% | 谁使用、谁付费、现有人工流程以及真实任务改善；访谈与试点只呈现已取得事实 |
| 赛道结合度 | 20% | 以太坊参与结果核验；开放方法和公共记录；BOT 主网材料可核查 |
| 表达质量 | 20% | 一条失败到恢复的现场流程；证据可展开；已实现、回放和后续计划清楚分开 |

材料包括项目说明、成员分工、目标用户、比赛新增工作；源码与组件来源及许可；环境依赖和启动步骤；可访问交互入口或视频；测试结果和覆盖边界。BOT 主网材料另包含网络、合约地址、部署及登记交易、事件和浏览器链接。部署本身不直接等于获奖。

建议答辩核心表述为：系统检查一个服务是否符合当前任务的来源、权限及数据要求；模型负责理解与选择，网关负责限制操作，验证器负责核对结果；公开记录提供可追溯的观测，结论仍可复核、更正并随条件变化失效。

**11 赛后建设停点**

第一阶段完成真实试点：选一个研究团队、几类固定只读数据，获取接入时间、失败影响及误拒绝反馈。第二阶段扩展验证器与部署来源证明：覆盖更多链上方法、受信构建、已授权的私有数据源；同时保持未知项和证据来源。第三阶段完善公共复用：多个独立验证者、验证者选择策略、争议、更正、撤销及公共可访问性。第四阶段再按客户需求增加团队权限、私有部署、付费服务及支持承诺。

不应把 token、质押、复杂经济机制或多 Agent 数量作为发展停点。更可持续的资产是接入多个平台的验证协议、真实失败与修复数据、可复核的验证器和客户工作流。数据优势必须建立在授权、可追溯标注和有效覆盖上，不能依赖收集大量无关日志。

17. [SLSA Security Levels v1.1](https://slsa.dev/spec/v1.1/levels)。本评估使用这个明确版本说明构建来源和防篡改层级，不宣称它是最新版本。
18. [Ethereum JSON-RPC API](https://ethereum.org/developers/docs/apis/json-rpc/)。区块标签、状态方法和节点调用约定。
19. [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898)。按区块哈希查询和规范链要求。

21. [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)。令牌透传、混淆代理、SSRF、重定向及 DNS 的安全指南。
22. [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785)。规范化 JSON 与哈希输入。
23. [BOT Chain 官方 Quick Guide](https://dev-docs.botchain.ai/docs/Developers/quick-guide/)。主网及测试网配置。
24. [MCP 官方规范](https://modelcontextprotocol.io/specification/latest)及[2026-07-28 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)。当前协议版本及兼容要求。
25. [NIST SP 800-218 SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)。安全开发实践框架，用于依赖固定、验证与工程交付管理。
